# RFC 2136 servers

tsigoat can stand in front of a name server that implements RFC 2136 itself,
such as BIND or Knot DNS: it authenticates the clients with their own keys,
checks its policy, then relays every update, signed with a key of its own, to
the server, which applies it. It is tested with BIND 9.

What tsigoat brings over the server alone:

- **The keys of the clients** stay out of the configuration of the server:
  in Kubernetes Secrets, one per client, renewed without reconfiguring the
  server.
- **The policy of tsigoat**: name patterns with `*` and `**`, prerequisites
  limited to the names that a key may update, the SOA only through a rule
  that names it.
- **An audit log and metrics** per client key.
- **Legacy algorithms stay on the client side**: a client stuck on HMAC-MD5
  talks to tsigoat, which signs with HMAC-SHA256 for the server.
- **The server stays out of reach** of the clients.

## How an update flows

1. tsigoat verifies the signature of the client, checks the structure of the
   update and the policy, as for any backend, and answers the requests that
   it turns down itself.
2. It relays the prerequisites and the updates, unchanged, in a message of
   its own, signed with the key of the backend, over TCP.
3. The server evaluates the prerequisites and applies the update atomically.
   tsigoat relays its answer to the client, signed with the key of the
   client:

| Answer of the server | Answer of tsigoat |
| --- | --- |
| NOERROR, YXDOMAIN, YXRRSET, NXDOMAIN, NXRRSET, FORMERR, NOTZONE | The same |
| REFUSED, NOTAUTH, NOTIMP, SERVFAIL, any other rcode | SERVFAIL |
| A TSIG error, an unsigned or unverifiable response, no response | SERVFAIL |

The client cannot fix what the second and third rows tell: the server does
not grant the key of tsigoat what the policy of tsigoat grants the client,
does not serve the zone, does not know the key, or fails. The error of every
such update is in the logs of tsigoat, and in the
[TsigoatBackendErrors](operations.md#tsigoatbackenderrors) alert.

A response that does not come in time, a connection that breaks, or a response
that does not verify or comes unsigned, once the update reached the server,
leaves the outcome unknown: the server may have applied the update. The update log tells so, and
the [TsigoatUncertainUpdates](operations.md#tsigoatuncertainupdates) alert
fires; a client that sends its update again finds the zone as the server left
it.

tsigoat answers the SOA queries of the zones with the SOA of the server, which
it queries over TCP, signed, at most every 30 seconds.

The server serializes the updates of a zone: tsigoat keeps no lock for the
zones of an `rfc2136` backend, so that several instances of tsigoat may relay
to the same server.

## Setting up the server

The server needs the key of tsigoat, and must let it update the zones. With
BIND, `tsig-keygen -a hmac-sha256 tsigoat.` prints the key statement, whose
secret goes to tsigoat too:

```text
key "tsigoat." {
    algorithm hmac-sha256;
    secret "...";
};

zone "example.com" {
    type primary;
    file "example.com.db";
    update-policy {
        grant "tsigoat." zonesub ANY;
    };
};
```

Grant the key of tsigoat what its clients need, and no more, for a second line
of defense: `grant "tsigoat." zonesub TXT;` suffices for ACME challenges.

## Configuration

```yaml
backends:
  - name: bind
    type: rfc2136
    rfc2136:
      server: ns1.example.com:53
      key:
        name: tsigoat.
        secretFile: /run/secrets/tsigoat/bind
zones:
  - name: example.com.
    backend: bind
    policy:
      - key: cert-manager.
        acme: ["example.com.", "**.example.com."]
```

[Configuration](configuration.md#backends) lists every setting.
`tsigoat check-config --backends` queries the SOA of every zone, signed: it
checks that the server answers for the zone, and knows the key.

## Limits

- The log of an update lists the updates as the client requested them, in
  `updates`, not their effect, which only the server knows.
- The server sees the updates coming from tsigoat; the client of each one is
  in the logs of tsigoat only.
- The zones must be served by their primary server, or by a server that
  forwards the updates to it.
